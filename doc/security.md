# Security check of the project server

What was examined, how, what was found, what was changed, and what is left. Done on 2026-11-14 and 15, on the code as of commit `848e74d` plus the fixes described here.

The subject is the server side of a project: `tools/serve-project.el` (the HTTP server in a native Emacs), `lisp/app-server.el` (what a project's `server.el` runs on), the scripts and proxy configurations that ship in a download, and the sample server in elisp-react (`examples/server`). The studio page itself (`js/studio.js`, the browser side) was read, not attacked.

## The situation that was assumed

The server listens on 127.0.0.1 and speaks plain HTTP. Either a developer runs it on their own machine and opens it in a browser there, or Caddy or nginx on the same machine publishes it (`PUBLIC_ORIGIN`, perhaps `WORKERS`). Who might attack:

1. a visitor without an account, who can send any bytes through the proxy;
2. a page of another site, open in the browser of someone who runs the server locally or is signed in to the published application;
3. a signed-in user of an application built on it;
4. another user of the machine the server runs on.

## How it was checked

| Method | What it did |
|---|---|
| OWASP ZAP 2.17 (Docker image `zaproxy/zap-stable`) | `zap-api-scan.py` (active: injection, traversal, command execution and so on) against an application with accounts, notes and uploads, described to it by an OpenAPI file, signed in; `zap-baseline.py` (passive) against its pages. Before and after the fixes. |
| Probes written for this server | About a hundred raw requests: some thirty ways to ask for files that must not be served, Host and Origin variants, 20 ambiguous or malformed framings, hostile bodies for the Lisp reader, cookies, plus floods of connections and of symbols. Before and after the fixes. |
| An independent reading of the code | A second reviewer who was given the code and the situation above, not the suspicions, and who verified what it found against a running server. |
| The shipped proxies | The fixed server behind Caddy 2.11 and nginx 1.30 with the shipped configurations. |

The two serious findings came from the probes. The independent reading reported neither; it looked at the first and set it aside as unreachable. A reading of the code, however careful, was not enough here.

## Findings

Severity is for the situation above. "Fixed" means: reproduced before, not reproducible after, and a test in `test/serve-project.test.mjs` ("what the security check found stays fixed") that fails if it comes back.

## What held, before any change

- **Files.** `server.el`, `server/`, `.data/` (databases, sessions, kept files), hidden files and anything outside the project: some thirty variants (`..`, encoded dots and slashes, doubled slashes, upper case on a case-insensitive disk, trailing dots and spaces, overlong UTF-8), and symbolic links that lead out. None got through.
- **Injection.** ZAP's active scan (120 rules passed, none failed): SQL injection, path traversal, remote file inclusion, OS command injection, server-side code and template injection, XXE, and the rest of its list. SQL in queries and bodies ends up as text in a parameter. Uploaded names such as `../../server.el` and ZAP's payloads became plain names inside `.data/files/`.
- **The Lisp reader.** 600 KB of open parentheses, 100,000 levels of nesting, circular structures, byte-code objects, `#.` and backquote forms: read as data or refused, never evaluated, no crash. (The cost in memory is finding 2.)
- **Sessions.** A forged or malformed session name is nobody; signing in while sending a session name of one's own choice gives a new one (no fixation); the database holds only hashes of session names; signing out and signing out everywhere work across workers.
- **Other sites.** A POST with a foreign `Origin` (also `null`, look-alike and wrong-case origins) is refused; there are no CORS headers, so no page of another site can read an answer. (Since then `CORS_ORIGINS` can name sites whose pages may: their requests come without cookies unless `CORS_CREDENTIALS=yes`. The list is exact origins, no patterns, and empty unless set.)
- **Header injection.** A line break in a header value, a cookie or a download's file name does not reach the response.

## What is left, knowingly

- **The page's scripts are not restricted.** The policy above says nothing about where scripts may come from (ZAP reports this as medium), and the page loads elisp-react and Emacs from `modeverv.github.io` without integrity checks, unless `./fetch-emacs.sh` made a local copy. Whoever controls that site controls the pages. An application that wants more sets its own `Content-Security-Policy`, which replaces the server's: for its pages and other files with `app-server-file-headers`, for answers of `/api/` with `app-server-set-header`; or at the proxy.
- **A POST without an Origin is accepted**, for programs that are not browsers. Browsers send one with every POST to another site, and those are refused. There is no CSRF token.
- **Other users of the server's machine** can connect to the port directly, past the proxy, and say anything in `X-Forwarded-For` or in a header a proxy would set to name the signed-in user. A machine with untrusted local users is not the place for this server.
- **What `server.el` does is its author's business**: `read` on a body (finding 2), a visitor's text as the URL for `app-server-fetch` (requests to wherever the server can reach), an uploaded file sent back as `text/html` (a page under the application's name; the default type and `:name` avoid it), a `GET` that changes things.
- **A session is whoever holds its cookie**, for thirty days or until it is ended. It is not tied to an address or a browser and is not renewed. `HttpOnly` keeps it from the page's scripts and `Secure` from plain HTTP; a visitor whose machine is read by someone else is that someone.
- **One thread.** A handler that computes for long holds up everyone; handlers that wait inside Emacs are turned away beyond 32 deep (503). Large answers are sent one inside the other in the same way (findings 15 and 16): with more than 32 of them under way the next visitor gets 503, and visitors who do not read can keep it so for as long as they keep coming back, 30 seconds at a time. With the shipped configurations and `PROXY_SENDS_FILES=yes` the proxy sends every larger file and this does not arise; Emacs alone (on a developer's machine, in a local network), or behind a proxy that was not told to send the files, has it.
- **Not examined:** the studio page and the wasm Emacs in the browser beyond reading; elisp-react's rendering (text is set as text, not as HTML, but that was not attacked); runs longer than a quarter of an hour; Emacs versions other than 31.1 here and 29 in CI; Windows.
- This was a check by the people who wrote the code, with tools. It is not a penetration test by someone paid to break in, and "nothing more was found" is not "nothing more is there".

## Since the check

- **2026-11-15, random bytes in the studio's tab.** `app-server-token` read `/dev/urandom` with a start position, which the browser's Emacs 30.2 refuses for a device, and in the tab fell back to Emacs's `random`, which is not a generator for secrets. Nobody but the tab's own page reaches that server, so nothing was exposed. It now reads without a start position, gets the browser's `crypto.getRandomValues`, and has no fallback; the browser test signs in in the tab, which fails without those bytes.
- **2026-11-15, tokens.** What the server has for signing in ends at sessions. The README ("Tokens") says what was tried about JWTs: one the application signs itself is possible in `server.el`, one signed by somebody else cannot be checked, and a token does not get a page of another site past the origin check (a preflight is answered with 403).
- **2026-11-15, parts of a file.** The server now answers a `Range` header for the project's own files (the page's Emacs reads its Lisp files as parts of one large file). The name goes through the same check as for a whole file, so nothing new is served: not `server.el`, not `.data/`, not what a handler sends. One range of bytes is understood (`bytes=START-END`, `bytes=START-`, at most 15 digits each); anything else gets the whole file, a start past the end gets 416. A part is read from the disk as it is sent, in pieces of 1 MB, like a whole file. The unit tests ask for parts at the edges of those pieces, past the end, and of a file that is not served; this was not scanned again with ZAP.
- **2026-11-15, compressed copies.** For a file that has `NAME.gz` next to it, the server sends that copy with `Content-Encoding: gzip` to a browser that takes gzip (`fetch-emacs.sh` makes such copies of the browser's Emacs). The copy goes through the same check as a file asked for by name, so a link out of the project is not followed and what is not served has no copy; it must be exactly `NAME.gz` in the same directory and not older than the file. The server compresses nothing itself, so there is no answer whose length depends on a secret mixed with what a visitor sent (the BREACH kind of attack needs that); answers from `/api/` are never compressed by it. Covered by the unit tests, not scanned with ZAP.

## The second check (2026-11-15): parts of files, compressed copies, large answers

The server had learned two things since the first check (a `Range` header, a `NAME.gz` next to a file), and a project's own copy of the browser's Emacs made it send large files to every new visitor. So it was checked again, on the code after commit `8a8ade3`.

| Method | What it did |
|---|---|
| OWASP ZAP 2.17 | The same application as before, plus files of a megabyte and more, a `.gz` copy, and a vendored Emacs. `zap-api-scan.py` with the static files in the OpenAPI description (path and `Range` and `Accept-Encoding` as parameters) and with injection into URL paths and headers switched on (`scanner.injectable=31`), which the first check did not have: some 9,200 requests each time. `zap-baseline.py`, and `zap-full-scan.py` (spider and active scan of the site). Before and after the fixes. |
| Probes | Some thirty forms of the `Range` header; parts of what is not served; a `.gz` that is a link out of the project, the copy of a file that is not served, of a directory, of a stale file; 300 requests at once; visitors who hang up at once (by closing, by a reset) or after the first bytes; visitors who never read; 1 to 300 first visits at once, each the 17 requests of a real one. Directly, through Caddy 2.11 and through nginx 1.30 with the shipped configurations. |
| Browsers | Chrome 157, Firefox 160, Safari 27.0, and Safari in the iPhone simulators of iOS 26.5 and 27.0, against a project with its own copy of Emacs and against one that takes Emacs from the public site: start, a click, a library required later, a second visit. A proxy in between wrote down every request and answer. |

ZAP's scans raised nothing of their own that was right, but the 500s in the server's log during the active scan led to finding 14, and looking for what else a large answer can do wrong led to 12, 13 and 15. As in the first check, the serious ones came from probes.

|---|---|---|---|---|
| 12 | High | **A visitor who hung up ended the server.** Writing to a connection that the other side has closed raises SIGPIPE. | 13 | High | **An error while writing an answer ended the server.** With the signal ignored, the same visitors made the write fail with an error. | 14 | Low | **A file's name with a slash after it gave 500** (`/app.el/`). Emacs says such a name is a regular file and then knows nothing more about it. ZAP's active scan, with path injection on. | 500, the word "error", the server went on. | 404. |
| 15 | Medium | **Visitors who do not read held the server.** Emacs sends one large answer at a time; while one waits for its visitor, the next is sent inside it, 32 deep at most, then `503`. And with `PROXY_SENDS_FILES=yes` (below) Emacs sends no large answer at all: 60 such connections through Caddy or nginx, and the next visitor is answered at once. |
| 16 | Medium | **Thirty first visits at once were about all the server managed**, for the same reason: every new visitor downloads 5 MB of Emacs. | Directly: 30 at once all got their files, of 60 half did not (`503`, connections refused). Through either proxy some of 20 did not. | The shipped Caddy and nginx configurations send `/vendor/` themselves, with its `.gz` copies and the parts of files that are asked for: 100 first visits at once (1,700 requests) all got everything through both. Sent by Emacs, the limit is as before. |

**Files sent by the proxy.** The way out of 15 and 16 that does not depend on which proxy it is: with `PROXY_SENDS_FILES=yes` the server decides whether a file may be sent, exactly as before, and answers with its name in an `X-Accel-Redirect` header and an empty body; the proxy sends the file. That holds for the project's own files above 16 KB (not pages) and for the files `server.el` answers with, after `server.el` decided. The name is under `/.files/`, which nginx serves from an `internal` location and Caddy only inside the handling of an answer that carries the header; asked for from outside, `/.files/server.el`, `/.files/.data/server.db` and the like are 404 through both, and the header does not reach the visitor. The shipped configurations also run four workers, and nginx limits one address to 600 requests at a time (Caddy has nothing built in for that). A proxy that is not configured for the header would pass an empty answer on, which is why it has to be switched on.

The sample server of elisp-react had finding 12 in the same form (a file of 43 KB was enough) and got the same fix; its filter already caught the error of finding 13.

What held: every form of `Range` gave the part, the whole file or 416 and never an error; no part and no copy of a file that is not served (`server.el`, `.data/`, `*.sh`, a link out of the project, `server.el.gz`); a `.gz` that is a link out of the project is not sent in place of its file; 300 requests for parts at once are answered. After the fixes, none of the 40,770 requests of ZAP's three scans was answered with 500 (69 before), and the server was running afterwards. ZAP's alerts are then those of the first check (the page's content security policy, see below), and one that is not right: "NoSQL Injection - MongoDB" (high) for `/?app.el[$ne]=`, because the page is the same whatever the query says. Nothing there is asked of a database.

The five browsers did the same thing down to the byte: 46 requests for two visits, the compressed copies, the Lisp files in parts (21 range requests, each with `Accept-Encoding: identity`), no whole package. From the public site, which is another origin for such a page, all five read on demand too. So none of them sends a preflight for the range request; GitHub Pages refuses preflights (405).

Not done: a real iPhone (the simulator has the Mac's memory; the module reserves 1 GiB of address space, which a phone may not give), Android, Edge; a scan through the proxies; the systemd unit.

## Doing it again

The regression tests run with `npm run test:unit`. For ZAP: describe the application's `/api/` in an OpenAPI file with `servers: [{url: "http://host.docker.internal:PORT"}]`, start the server with `PUBLIC_ORIGIN=http://host.docker.internal:PORT`, and

```sh
docker run --rm -v "$PWD:/zap/wrk:rw" zaproxy/zap-stable zap-api-scan.py -t openapi.yaml -f openapi -r report.html \
  -z "-config replacer.full_list(0).description=auth -config replacer.full_list(0).enabled=true \
      -config replacer.full_list(0).matchtype=REQ_HEADER -config replacer.full_list(0).matchstr=Cookie \
      -config replacer.full_list(0).regex=false -config replacer.full_list(0).replacement=session=NAME-OF-A-SESSION"
docker run --rm -v "$PWD:/zap/wrk:rw" zaproxy/zap-stable zap-baseline.py -t http://host.docker.internal:PORT/ -r baseline.html
```

For the second check, the OpenAPI file also named static files (with the path, `Range` and `Accept-Encoding` as parameters), `-config scanner.injectable=31 -config scanner.scanHeadersAllRequests=true` was added to `-z` so that paths and headers are attacked too, and `zap-full-scan.py -t http://host.docker.internal:PORT/` ran with the same `-z`. Read the server's log afterwards: a `500` there is a finding even when ZAP reports none (finding 14). What ZAP does not try at all is to leave in the middle of an answer or not to read one; `test/serve-project.test.mjs` ("visitors who hang up ...") does.
